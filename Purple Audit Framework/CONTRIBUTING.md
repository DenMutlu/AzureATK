# Contributing to AzureATK

Thank you for contributing to AzureATK.

This project is intended to grow into a practical, production-safe Azure and Entra ID audit framework. Contributions that improve safety, clarity, repeatability, and usefulness are welcome.

## What kinds of contributions are useful

Contributions may include:

- methodology improvements
- safer validation workflows
- additional audit domains
- better reporting templates
- documentation fixes
- tool references and comparisons
- production-safe demo ideas
- corrections to assumptions or terminology

## Guiding principles

When contributing, please keep these principles in mind:

- **Production-safe first**
- **Methodology before tooling**
- **Clarity over complexity**
- **Evidence-driven recommendations**
- **Authorized use only**

## Before you contribute

Please make sure your contribution:

1. fits the production-safe philosophy of the project
2. is clearly documented
3. explains assumptions and scope
4. avoids destructive or uncontrolled actions in production guidance
5. is understandable by other practitioners

## Preferred contribution areas

### Documentation
Improve wording, structure, readability, and examples.

### Methodology
Refine the 5-phase framework, add validation types, or improve audit logic.

### Tools
Add tools with clear notes on:
- purpose
- strengths
- limitations
- permissions required
- production-safety considerations

### Templates
Improve audit trackers, finding templates, and presentation structures.

### Demos
Add short, safe, reproducible demonstrations that validate exposure, controls, logging, or detection.

## How to contribute

### Option 1: Open an issue
Use issues to propose:
- a new audit domain
- a missing validation step
- a tooling improvement
- a documentation correction
- a structural change to the repo

### Option 2: Submit a pull request
Pull requests should be:
- focused
- clearly described
- easy to review
- aligned with the repository purpose

## Pull request recommendations

When opening a pull request:

- explain what changed
- explain why it matters
- mention any assumptions
- mention whether the change affects production safety
- keep changes scoped where possible

## Style guidance

Please aim for:

- concise and practical language
- explicit assumptions
- minimal jargon where possible
- repeatable steps
- safe-by-design guidance

## What to avoid

Please avoid contributions that:

- promote destructive testing in production
- include uncontrolled phishing procedures
- encourage unsafe privilege escalation in live tenants
- rely on vague claims without evidence
- turn the repository into a tool dump without methodology

## Code of conduct

Be respectful, practical, and constructive.

This project benefits from diverse field experience, and disagreements are welcome when they improve safety, quality, or accuracy.

## Final note

AzureATK is meant to be a living framework.

If you have a better method, a safer way to validate a control, or a clearer way to document a real-world audit, please contribute.
